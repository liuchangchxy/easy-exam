# AntiGravity 项目执行流程

本文是 `AGENTS.md` 的执行手册。它不新增产品需求，只规定如何把已确认的需求变成可审查、可验证的代码批次。

## 1. 文档职责

| 文件 | 记录什么 | 不记录什么 |
|---|---|---|
| `AGENTS.md` | 长期 AI 规则、保护线、复杂度开关 | 某个批次的全部细节 |
| `SPEC.md` | 用户确认的产品行为、业务规则、验收条件 | 当前进度、猜测、测试结果 |
| `docs/REQUIREMENTS_TRACEABILITY.md` | SPEC 对应源码、测试、运行证据和缺口 | 新产品规则 |
| `TESTING.md` | 测试层级、命令、证据口径和 DoD | 过期的固定通过数字 |
| `DECISIONS.md` | 已确认的重要决策、背景和影响 | 日常进度 |
| `docs/superpowers/plans/` | 可独立验收的单批计划 | 产品愿景或大而全架构 |
| `docs/research/` | 外部源码审计和总体吸收路线 | 未证实的复用声明 |
| `docs/AGENT_COLLABORATION_PROTOCOL.md` | 双 Agent 协作协议、五大协调状态与停止条件 | 临时需求或代码变更 |
| `docs/optional/` | 触发式的安全、可靠性、并行规范 | 所有任务的默认负担 |

## 2. 需求批次流程

### 2.1 探索或诊断

只读检查当前代码、SPEC、测试和证据，不改产品规则。发现歧义时列出 2～3 个互斥选项，等待用户确认。

### 2.2 需求确认

把已确认的用户行为写入 SPEC，用“触发—输入—结果—失败/离线行为—验收”的句式；把实现状态放入追踪矩阵。不要因为代码已经存在就把需求写成已完成。

### 2.3 实施前

1. 读取 `AGENTS.md`、相关 SPEC、`TESTING.md`、追踪矩阵和活动计划。
2. 执行 `git status --short` 和相关 diff，保留所有既有工作树改动。
3. 核对计划引用的路径、路由、表、组件、测试和外部 commit 仍然存在。
4. 跨文件高风险变更先执行 checkpoint。
5. 触发时启用数据安全、可靠性、Multi-Agent 或 OSS 规范。

## 3. 计划与实现

每个叶子计划必须能独立审查和测试，放在 `docs/superpowers/plans/`。实现节拍如下：

1. 先写或补回归测试。
2. 运行目标测试，确认失败原因真实对应缺口。
3. 实现最小变更，禁止删除旧测试或放宽断言。
4. 做同类实现的全局扫描，检查用户隔离、事务、幂等、离线降级和 UI 使用链路。
5. 运行计划中的目标测试，再按范围运行全套相关测试。
6. 用真实源码、测试输出和运行结果更新追踪矩阵。

发现新产品需求、数据语义变化、许可证不清或外部副作用时，暂停当前批次，回到需求确认门，不在实现过程中自行裁定。

## 4. OSS 吸收流程

开源工作以 `docs/research/OSS_REUSE_AUDIT.md` 和 `OSS_REUSE_ROADMAP.md` 为基线，不从头泛扫所有项目。每个候选必须明确：

- 仓库、固定 commit、源文件和许可证；
- 是源码复用、实质改编、行为参考、保留自研还是不采用；
- 适配边界、归因/许可证保留方式和测试证据；
- 与 SPEC 的对应关系和未决风险。

没有许可证或不兼容时不复制源码；只参考行为也要明确标记为行为参考。

## 5. 阶段结束报告

```text
批次/计划：
对应 SPEC 条目：
实现了什么：
源码复用 / 行为参考 / 无：
改动文件：
测试命令及 pass/fail/skipped：
真实浏览器 E2E：
追踪矩阵是否更新：
尚未完成、未运行或需用户决定：
工作树中本批次以外的既存变更是否保留：
```

规划完成不代表代码完成；真实测试未运行或存在 skipped 时，必须在报告中保留缺口。
