## 2. 编号体系

编号是跨册引用的唯一方式，**分册之间不复制正文**。

| 前缀 | 含义 | 编号段 |
|---|---|---|
| `FN-` | 功能 | 题库 1xx · 学习 2xx · 模考 3xx · 协作实例 4xx · 资料设置 5xx · 全局外壳 6xx |
| `BR-` | 业务规则 | 同上按域分段 |
| `OP-` | 操作与交互 | 同上按域分段（全局交互集中在 6xx） |
| `ST-` | 状态 | 同上按域分段 |
| `PR-` | 权限 | 同上按域分段 |
| `GAP-` | 需补齐/修正项 | 同上按域分段；80 册做全量汇总与去重 |
| `Q-` | 需用户裁定的未决问题 | 同上按域分段；80 册做全量汇总 |

引用示例：「错题专项的服务端集合约束见 `BR-209`」；「返回行为见 `OP-602`」。

## 3.1 现状基线（读诊断文档前必读）

本地源码树的当前 HEAD 就是 **v1.0.24 发布版本身**（`feat(ux): core UX redesign P1-P6 and release 1.0.24`）。因此：

- `UX_CORE_REDESIGN` 的 **§5「各域诊断」描述的是重设计之前的状态，不是现状**；
- **§9–§14「P1–P6 实施记录」是已经落地的修正**，属于现状；
- **§14.3「刻意没做的」与 §14.4「已知残留」是真实存在的能力边界与残留**，是本规范 GAP 清单的主要来源之一。

判定一条问题是否算「现状缺陷」：只有 ① 实施记录之后仍未解决（含 §14.3/§14.4 明确列出的），或 ② 实施记录未提及、由本次读代码新发现的问题，才进 GAP，且必须附 `file:line`。

原型（OpenDesign 项目）同样基于 v1.0.24 构建。若发现原型与生产代码的信息架构不一致，登记为 GAP，类别「配置与实际不一致」。

> ⚠️ **注意区分「源码现状」与「线上实例现状」**：本机 `127.0.0.1:3000` 上跑的是一个**早于本地 HEAD 的构建**（实测 `/api/v1/admin/*`、`/api/v1/sessions` 返回 404，`/auth/me` 不返回 `is_admin`）。因此凡涉及权限面、实例管理、会话管理的「现状」判断，**一律以本地源码为准**；线上实例只用于确认接口契约与旧行为，不得用它否定源码里的已实现能力。

## 4. 本轮工作方式（留档）

- 六个分域分析员并行工作，每个都必须同时读三类材料：生产代码、产品文档、当前原型，并**真实用浏览器驱动原型**跑过本域的每条路径。
- 主 Agent 负责整合：统一术语、边界与语义，裁决跨域规则冲突，裁决结果写入 70 册。
- 独立复查由未参与编写的角色执行，核对「功能是否闭环、规则是否互相矛盾、是否漏掉低频与异常分支、是否存在因现有产品没做所以没写的遗漏」。

## 6. 本轮产出摘要（2026-11-26）

- **工作方式**：六个分域分析员并行，每个都同时读生产代码（本地 HEAD = v1.0.24 本体）、产品文档，并用真实 Chromium 驱动原型跑过本域每条路径；主 Agent 整合跨域规则并裁决冲突；独立复查由未参与编写的角色执行。
- **规模**：9 个文件，约 4 850 行；**120 个功能定义**，全部带七字段闭环模板；147 条业务规则、84 条操作交互、45 个状态、46 条权限规则、165 条缺口、51 条未决问题。
- **独立复查**：由未参与编写的角色执行，抽验 18 条缺口的 `file:line`、核对跨册矛盾与编号断链。**复查推翻了 3 条我方断言**（题库「改设置/归档」的权限判据、模考会话状态集、题库归档是否要求输入库名），以及 1 条把旧构建观测当缺陷的误报（`GAP-613`）；全部已按结论修订。修订留痕见本节与 `80` 册 §1.1 对账表。
- **证据纪律**：每条缺口都附 `file:line` 或原型页面；诊断文档的「改前状态」未被当作现状；本机运行实例因早于 HEAD 已单独登记为部署项，未用它否定源码里已实现的能力。
- **未决问题集中在 `80` 册 §6**，共 51 条，每条附候选方案、推荐与理由、以及未裁定时的默认行为——保证在用户回复前产品仍可继续推进。
