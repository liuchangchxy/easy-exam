# AntiGravity：OSS 选择性复用总计划提示词

用途：将已经完成的 OSS 代码级调研转化为覆盖全局、分阶段可执行的实施计划。此提示词只允许调研现状、综合证据和编写计划；**不授权实现代码，也不要求重新做全量开源调研**。

复制下面整段到 AntiGravity 新对话中执行：

```text
你在易考宝仓库中负责制定“选择性吸收开源项目优点”的全局实施计划。严格遵守根目录 AGENTS.md 和 docs/ANTIGRAVITY_WORKFLOW.md 中“OSS 全局实施计划阶段”。

## 目标

以现有代码级调研为事实起点，把本项目已确认的产品需求与候选 OSS 的源码/行为价值对应起来，形成一份覆盖所有候选项目、可审阅、可分阶段落地的总计划。这里的“吸收全部”是：把所有经审计适合本项目的优点都安排到明确处置和计划中；不是复制全部仓库，不是每个项目都必须贡献代码，也不是一轮改完所有模块。

现有调研已经完成，首先读取并复用：
- `AGENTS.md`
- `SPEC.md`
- `TESTING.md`
- `docs/REQUIREMENTS_TRACEABILITY.md`
- `docs/research/OSS_REUSE_AUDIT.md`
- `docs/research/OSS_REUSE_ROADMAP.md`
- `docs/ANTIGRAVITY_WORKFLOW.md`
- `docs/superpowers/plans/` 中与路线图候选相关的既有计划

审计记录了候选仓库、固定 commit、代码路径、许可证和当前采用结论。不得把工作退回“重新下载/通读全部 12 个仓库”。先核对当前代码和文档是否仍与已有记录一致；仅对路线图中仍待决、且会影响计划的具体文件做定向复核。若确需新候选或新源码证据，先说明现有证据为何不足，并把补查限制在那个候选/文件。

## Sub-agent 分工（若当前环境支持，必须派发）

所有 agent 只读，不得修改任何文件。分别派发以下互不重叠任务，不要让每个 agent 重复全量阅读所有仓库：

1. **现状与需求映射 agent**：只根据当前工作树、`SPEC.md`、`REQUIREMENTS_TRACEABILITY.md`、`OSS_REUSE_ROADMAP.md`，核验每个候选对应能力的需求状态、代码/测试实现状态和缺口。输出候选逐项表，每项附仓库相对路径及行号；不要重新审外部项目。
2. **剩余源码复用 agent**：只核查路线图中“尚未落地且仍可能直接适配”的候选与具体源文件，优先核验 MiaowTest 的对话/消息模型。报告固定 commit、精确源路径、许可证、可复用的最小代码/模型边界、改造代价及不适配点。不得扩展到无关候选或复制代码。
3. **实施顺序与验收 agent**：只审查现有需求追踪、测试策略及既有单批计划，识别依赖顺序、数据迁移/兼容风险、每阶段必须具备的自动化与真实用户链路验收。不得新增或改变产品需求。

每个 agent 必须返回：结论、证据路径和行号、外部来源 commit/license（如适用）、不确定项。若 sub-agent 功能不可用，明确报告不可用，并由你按以上三个边界依次做只读核查；不得声称已委派。

主 agent 必须独立审阅、去重并裁决 agent 输出。不同 agent 的结论冲突时，回到源码/需求/测试证据核实；不得简单拼接，也不得选择证据更弱的说法。agent 的建议不等于用户已经确认的新需求。

## 必须遵循的采用分类

对路线图中的每个候选和能力，只能明确归类为以下之一或组合，并给出证据：
- **源码直接复用/改编**：精确源文件、固定 commit、许可证、目标文件和归属保留方式都明确；只有许可证允许且技术边界合适才可安排。
- **行为/测试模式参考**：说清楚参考的行为或测试，不得称为复制或源码移植。
- **保留本项目已有实现**：说明比较依据、已有实现位置和为什么不替换。
- **不采用/关闭**：说明产品不匹配、许可证、维护成本或缺少 SPEC 需求等理由。
- **待用户确认/待证据**：指出唯一需要确认的问题或具体缺失证据；不得伪装成已批准开发任务。

AGPL/GPL、无许可证或许可证不清的代码不得直接并入本项目；若是行为参考，应与源码复制严格分离。不得为了“吸收所有项目”引进 SPEC 没有支持的产品功能。

## 计划产物和范围

创建或更新唯一的跨项目总计划：`docs/research/OSS_REUSE_MASTER_PLAN.md`。必要时仅在 `OSS_REUSE_ROADMAP.md` 增加指向总计划的链接或基于证据修正事实状态，不要复制两份完整路线图。

规划阶段严禁修改业务代码、测试实现/预期、依赖、API、数据库或 SPEC 产品规则。不得删除、放宽测试，不得将候选源码复制到本项目。若发现审计或追踪矩阵有事实错误，计划中列出精确证据和最小修正建议；只改对计划正确性有直接影响的事实，不顺便重写文档体系。

总计划必须覆盖路线图中的全部候选（即使结论是“不采用”），并至少包含：
1. 本计划目标、范围、不做事项、采用分类定义和文档职责；
2. 候选逐项矩阵：候选/能力、固定 commit 与源路径、许可证、关联 SPEC 条目、当前代码和测试证据、采用方式、拟处理批次、状态；
3. 当前已完成项与其可核验证据，不能把行为参考写成源码复用；
4. 尚待实施的工作分阶段排序。每阶段说明目标、具体能力、拟触及代码边界（可先定位到模块/文件；不确定的标待核实）、前置依赖、数据迁移/兼容性、许可证义务、测试层级和明确验收条件；
5. 对无 SPEC 缺口、不适配或许可证不可接受的候选，明确关闭而不是制造工作；
6. 必须由用户确认的产品/许可/数据语义问题，与可由工程计划自行决定的实现细节分开；
7. 每阶段对应未来独立的 `docs/superpowers/plans/` 叶子计划建议，但不得把所有叶子批次合并成一次代码执行；
8. 风险、跨阶段依赖、停止条件、完成定义，以及如何逐批更新追踪矩阵/审计/路线图/README。

每项事实必须可追溯到文件路径和行号；外部事实还需固定 commit、源路径及许可证。验收必须是可运行或可观察的，不要写“质量高”“完整吸收”“测试全绿”这类不可核验目标。当前没有实际运行的测试只能列为计划门槛，不能报告成已通过。

## 完成前自审

- 检查路线图所有候选是否逐项进入矩阵，是否错误遗漏未采用项。
- 检查源码复用、行为参考、保留自研和不采用是否清楚分开。
- 检查每项拟实施工作是否映射到已确认 SPEC；否则改为待用户确认或关闭。
- 检查计划顺序是否先解决依赖，而不是按仓库/模块名机械排列。
- 检查没有因 agent 建议而新增产品需求，没有把一次总计划变成一次性大改。
- 检查主文档不存在占位符、矛盾、无证据断言和虚构完成状态。
- 保留并尊重当前工作树所有既有改动；禁止 reset、clean、restore、checkout 覆盖。

- 既有工作树变更是否完整保留。

完成计划后停下来等待用户审阅，不要自行开始第一阶段实现。
```
